What exists today

Operational domains in RackMarshal 1.0

Each enabled domain has a collector and incident-processing path. Proxmox, ZFS, backup/PBS and Home Assistant also include explicit observation, comparison and event stages; hardware and mount use integrated pipelines.

Virtualization

Proxmox VE

Records cluster-resource observations, compares verified resource state, and opens or recovers incidents when expected VM or container status diverges and returns.

Storage

ZFS

Observes pool state through SSH, compares verified baselines, records status-change events, and tracks pool incidents through recovery.

Backup

Backup / PBS

Observes backup resources and PBS state, compares them against verified state, and tracks backup incidents and recovery.

Automation

Home Assistant

Records Home Assistant observations, compares expected resource state, records changes, and tracks incidents through recovery.

Systems

Hardware health

Tracks configured NVMe devices and temperature thresholds, including urgent conditions and sample-based recovery.

Availability

Mounts

Checks configured host, VM and container mounts, detects missing or mismatched sources, and tracks mount incidents through recovery.

See RackMarshal in action

A local API exposes runtime health and assembled operational status.

A verified base installation starts the local status service. The health endpoint is deliberately simple; the status endpoint assembles RackMarshal operational state from the local database and configured domains.

Health

GET /health

{ "status": "OK", "generated_at": "…" }
Status

GET /status

Returns the locally assembled RackMarshal status payload for the runtime and available operational domains. The default API remains bound to 127.0.0.1:9110.

Designed for infrastructure you control

Local first by design.

RackMarshal is designed to operate without turning your infrastructure telemetry into a dependency on somebody else's hosted service.

Early adopters wanted

Put RackMarshal into infrastructure it wasn't built on.

We’re looking for technically experienced users willing to install RackMarshal, configure it against real systems, challenge its assumptions, and find the environments we didn’t anticipate.

Install the 1.0 release bundle

Start with a Debian/Ubuntu-compatible system using systemd and Python 3.11+.

Verify the base runtime

Confirm the status service, notification timer and local /health endpoint.

Configure one domain

Enable a domain explicitly, add its site-specific credentials or SSH access, and validate configuration before collection.

Generate observations and report what happens

Use RackMarshal in a real environment and report installation, configuration or incident-lifecycle failures as GitHub issues.

Important current boundary

A successful base installation proves the RackMarshal runtime, database, status API and notification queue can run. It does not automatically configure access to Proxmox, PBS, Home Assistant, ZFS, hardware or mount targets.

Those integrations require site-specific configuration and credentials. The installer does not copy production credentials or discover your infrastructure automatically.

Built from real infrastructure

From one working environment to an open project.

RackMarshal was created by Michael Poteet after developing an operations system for his own self-hosted infrastructure. What began as a way to track health, failures and recovery across Proxmox, ZFS, backups, Linux systems and related infrastructure evolved into RackMarshal.

RackMarshal is now developed in the open so that operational model can be tested across infrastructure other people operate.

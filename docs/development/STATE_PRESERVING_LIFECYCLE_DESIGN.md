## Transaction phases and crash boundaries

1. PLAN/VALIDATE: acquire a root-only exclusive lifecycle lock; refuse any unfinished transaction. Use a trusted system interpreter with isolated/no-site startup. Validate full candidate inputs, exact old artifact provenance, installed code/metadata/interpreter/ownership, config and referenced credential/catalog paths, loaded units and overrides, free space and same-filesystem constraints. Never run an unvalidated legacy venv. Compare every migration ID/checksum, ledger and SQL schema with the supported pair; reject missing/unknown/mismatched entries. Check SQLite integrity. A plan has no service or application-state mutation.
2. STAGE: create exclusive durable root-private transaction storage outside the service-writable DB directory and on the same filesystem as executable activation, e.g. /opt/rackmarshal/.transactions/<id>. Retain pinned old/new inputs, manifests, version/hash identity and journal with fsync(file)+fsync(parent) at each transition. Build a separate pipless candidate venv; verify complete wheel inventory and root-run fixture acceptance. Keep all transaction/credential backups root-private. Defer the actual service-UID traversal/import probe until guarded activation at the final service-readable path; do not grant service access through the private transaction directory. Never overwrite active code to install dependencies.
3. MAINTENANCE GUARD: before the first service stop or rename, persist a narrowly scoped maintenance marker and validated systemd condition drop-ins for every supported RackMarshal timer/service including instantiated domain targets. Reload and verify effective configuration. The condition rejects startup while that transaction marker exists, including after reboot. It changes no enablement; record exact pre-existing active/enabled states. Reject unknown writers/units and pre-existing drop-in collisions. Crash at any later phase leaves the marker and workloads blocked; no automatic boot recovery starts collectors. This guard requires disposable reboot/race tests, not an assumed systemd guarantee.
4. QUIESCE: stop timers first, close activation races, boundedly drain known jobs, then stop status/other supported writers/readers and confirm no active jobs/writers. Do not blindly kill a timed-out writer and proceed. On uncertainty, retain old code, maintenance guard and evidence for explicit recovery. Managed-unit cooperation cannot exclude arbitrary external root scripts; support requires no unmanaged database writers. Refuse detected writers.
5. BACKUP_VERIFIED: snapshot full config and authorized credential/catalog files with metadata into private storage without logging values. Open SQLite read-only and use SQLite backup API while quiesced; do not copy a live DB file alone or ignore WAL. Verify backup with integrity_check, full schema/ledger and deterministic logical table-content comparison (all incident/history/notification tables), plus cryptographic hashes. Reopen a second restored private copy and verify again. Preserve raw source sidecars/evidence where applicable; never delete source WAL/SHM as a shortcut. Sufficient free storage and successful restoration rehearsal are prerequisites for activation.
6. ACTIVATE: database/config/credentials stay in place and are not migrated. Rename old venv to retained rollback storage, then staged venv to /opt/rackmarshal/venv, recording intent before and observed identities after each rename. These two renames are NOT collectively atomic; the maintenance guard and durable recovery journal cover the absent-path interval. Use same-filesystem renames with directory fsync. Unit payload replacements are per-file atomic, journaled with prior hashes/metadata and verified. Preserve known custom overrides rather than overwrite them. Unknown current bytes cause refusal.
7. ACCEPT: verify installed bytes, console entry points and service-UID imports at their final path. Run isolated fixture migrations/lifecycle and protocol tests against private DB only. Temporarily allow only the status service for bounded read-only live readiness if it was previously active; all processing/notification timers and oneshots remain guarded. Require live data/config/credential invariants, appropriate empty/unknown status semantics and unchanged recorded incidents. No manual notification replay. Roll back on readiness failure; readiness is not sufficient by itself.
8. COMMIT/RESUME: persist acceptance before selectively lifting guards; restore only prior active/enabled states, timers last. Never enable a new timer/domain or run an inactive notification oneshot as a postinstall hook. Record each restoration and final verification; mark COMMITTED only after both package acceptance and runtime restoration succeed. Interrupted resume is RECOVERY_REQUIRED, not PASS. Retain transaction, backups and old code; no automatic retention purge.

Venv relocation must be explicitly solved and tested: generated console-script shebangs, activation scripts and RECORD hashes can contain staging paths. Do not assume a venv is relocatable. Extend the pinned bootstrap installation scheme to generate known final-path entry points and corresponding RECORD entries while writing into staging; verify scripts before activation and execute each supported entry point after activation. Alternatively produce the final tree under the guarded final path only after saving old code, with full journal recovery. Prefer final-path-aware staging; no general string replacement across code or permissive RECORD edits.

## Rollback, re-upgrade and database boundary

Ordinary rollback restores only exact retained application/unit bytes and the recorded runtime configuration. It preserves the CURRENT database, config and credentials, including observations and incidents appended after upgrade. Identical migrations mean no schema downgrade is needed, but do not establish behavioral compatibility. Review old/new JSON payload, incident, baseline and notification semantics and prove the restored processors preserve integrity incidents correctly. The known ZFS false-recovery bug is a mandatory rollback regression: older code must not resume processing that would falsely recover a positive-error incident. If that behavior fails, application restoration may end in explicitly ROLLED_BACK_QUIESCED with affected workloads still guarded, not a fully qualified resumed rollback PASS. A safe resume path needs a compatible corrected rollback target and its own artifact/behavior evidence; it cannot be invented by rewriting receipts. Full release rollback acceptance stays blocked until the intended supported path is resolved. Revalidate the actual schema/ledger before rollback, and use expected-current-byte guards to refuse unrelated subsequent code/config/unit changes. Re-upgrade uses a new transaction, preserving prior transactions and all intervening state.

Failure before application activation requires no DB restore. Failure after activation normally still requires only application rollback because this lifecycle never writes the live DB. A verified backup is insurance and a qualification proof, not permission to rewind recorded history. Backup restore is a separate recovery action requiring exclusive quiescence, exact backup validation, saved current DB and an explicit no-new-writes proof. Any uncertain/intervening writes require operator investigation and approval; never overwrite newer incidents to make rollback pass.

Pending or irreversible migrations are REFUSED by this candidate. Future schema-changing upgrades require a separate reviewed migration plan: consistent shadow DB, complete migration transaction/ledger semantics, compatibility classification and post-cutover writes policy. A schema-incompatible old app cannot be made safe by silently restoring a pre-upgrade DB. Do not implement a generic --force or --allow-data-loss switch here.

Explicit recover uses only recorded old/new hashes and journal states to finish a known commit or restore old application units. Corrupt/missing backups, unrecognized current files or an unproven DB state fail closed; preserve maintenance guard and receipts. Test SIGKILL/reboot at every persisted phase. Do not claim atomicity across code, units, DB and systemd.
